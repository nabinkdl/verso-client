# .brain.md — Frontend (`apps/ui`)

## 1. Snapshot

- React 18 + TypeScript + Vite 5 single-page app. Mobile-width social UI, no router, no state library.
- **API-backed:** auth (login/register/forgot/reset), feed, posts, likes, comments (add/delete), profiles, follow/unfollow, user search, and chat (conversations, message history, live delivery, typing, read receipts).
- **Local prototype only:** reels ranking/saves, notifications, pages/communities, marketplace (listings, cart, orders), comment editing. Theme persistence is real but client-only.
- API contract and planned endpoints: [`docs/API-DESIGN.md`](../../docs/API-DESIGN.md). Run instructions: [`docs/RUNNING.md`](../../docs/RUNNING.md).

## 2. Run & verify

## 3. Architecture map

```text
src/
├── App.tsx                 # screen state machine + most app state; default export wraps AppContent in PageProvider
├── main.tsx                # React root (StrictMode) — no providers here
├── types.ts                # shared UI types (User, Post, Page, Product, Order, …)
├── data.ts                 # mock data + CURRENT_USER_ID = 'u1' (notifications, pages, products, cart)
├── index.css               # Tailwind entry + light/dark CSS variables
├── components/             # one file per screen + shared pieces (Avatar, Dialog, BottomNav, …)
├── contexts/PageContext.tsx# in-memory pages/membership/roles/events (React context + setState)
└── services/
    ├── api.ts              # fetch wrapper, typed API client, DTO → UI mappers
    ├── chatSocket.ts       # Socket.IO singleton (JWT handshake, connect/disconnect)
    ├── postService.ts      # pure array helpers for local post/comment mutations
    └── notificationService.ts # pure helper: addNotification
```

Big screens live in one file each and are large (Marketplace ~860 lines, PageView ~1450). Prefer extracting shared subcomponents over adding to them.

## 4. State & data flow

### Auth

- Token stored in `localStorage` under **`verso-token`** via `getToken()` / `setToken()` in `services/api.ts`.
- Boot: if a token exists, `GET /auth/me` → `setCurrentUser`, merge into `users`, `loadFeed`, then `activeScreen = "home"`. A failed boot **clears the token** and falls back to login.
- There is **no refresh token**; expired tokens surface as request errors and are not auto-cleared mid-session.
- `currentUserId = currentUser?.id ?? CURRENT_USER_ID` (`'u1'`) — the fallback is for the pre-auth demo state.

### API client

- `request<T>()` prefixes `VITE_API_URL`, adds `Authorization: Bearer` when a token exists, and sets `Content-Type` only when a body is sent.
- Errors become `Error(message)`; array `message` from Nest validation is joined with `", "`.
- No retries, no abort/cancellation, no 401 interceptor.
- Endpoint methods are grouped on the `api` object; add new endpoints there, never inline `fetch` in components.
- Types: `ApiUser`, `ApiProfile`, `ApiPost`, `ApiComment`, `Paginated<T>` mirror the backend. Mappers `toUiUser`, `toUiPost`, `toUiComment` convert API → UI types (notably `mediaType` `"IMAGE"/"VIDEO"` → `"image"/"video"` and ISO dates → `number`).

### Screen routing

- No router: `activeScreen: Screen` union + a chain of `{activeScreen === "x" && <XScreen …/>}` in `App.tsx`.
- `Screen` union: `login | register | forget | reset-password | home | search | newPost | reels | notifications | chat | profile | pages | marketplace | admin`.
- `admin` is in the union but has **no route/render branch**; admin/team management lives inside the Pages screens.
- `BottomNav` tabs: home, pages, reels, chat, profile. Search, notifications, new post, marketplace are opened from other screens (marketplace reuses the `pages` tab highlight).
- Password reset is entered via `?resetToken=…` on the URL; the token is cleared with `history.replaceState` after a successful reset.

### Feed loading

`loadFeed` = `GET /posts?limit=20`, then one `GET /posts/:id/comments` per post (`Promise.all`), then merges authors into `users`. There is **no infinite scroll** and no cursor usage yet — adding pagination means touching `loadFeed` and `HomeScreen`.

### Chat flow

- `App.tsx` fetches `/conversations` on login and whenever a `conversation:updated` socket event arrives; it passes the list to `ChatScreen`.
- `ChatScreen` fetches the thread history when opened, emits `conversation:join`, marks the thread read, and subscribes to `message:created` / `typing` for that thread only.
- Sending uses `message:send` with an ack. There is **no optimistic bubble**: the message appears from the ack or the broadcast. The ack timeout is 15s and a timeout must **not** trigger an HTTP resend (duplicate risk); it refreshes the list instead.
- Only a disconnected socket falls back to `POST /conversations/:id/messages`.
- `disconnectChatSocket()` runs on logout; the socket is a module singleton, so do not create ad-hoc clients in components.

### Optimistic updates

- Like: optimistic local update from `{ liked, likeCount }`; on network failure it **silently falls back to a local toggle** (no error shown).
- Edit/delete post and delete comment: optimistic with rollback via `window.alert` on failure.
- Add comment: server-first, then local insert.
- Comment **edit is local-only** (the API has no endpoint).

## 5. State ownership (critical when wiring new APIs)

| Domain | Source of truth today | Notes |
| --- | --- | --- |
| Current user, posts, comments, follows, user search | API | `App.tsx` state + `api.ts` |
| Saved posts (`savedPosts`) | Local `useState` | IDs only; lost on refresh |
| Notifications | Local `initialNotifications` + `pushNotification()` | Generated for local actions, not from server |
| Conversations + messages | API (`/conversations`) + Socket.IO | `App.tsx` keeps the conversation list; `ChatScreen` owns the open thread's messages |
| Pages (members, roles, invites, events, analytics) | `PageContext` in memory | Seeded from `initialPages`; resets on reload |
| Marketplace products / orders | Component state in `MarketplaceScreen` | Seeded from `initialProducts` |
| Marketplace cart | `App.tsx` state | Seeded from `initialMarketplaceCart` |
| Reels | Derived from `posts` (6 newest, **not** filtered to video) | Likes/comments hit the API |
| Theme | `localStorage` `verso-theme` + `.dark` on `<html>` | |

`users` is a merged directory seeded with 42 fake `AdminUser`s (`u1`…`u42`). API users are merged in by `mergeUsers`, which preserves local follower arrays when the API sends none. **Some components still receive `CURRENT_USER_ID` (`'u1'`) instead of the signed-in user's id** — see gotchas.

## 6. Styling conventions

- **Inline styles everywhere**, with `style={{ … }}` and CSS variables from `index.css` (`var(--bg)`, `var(--text-muted)`, `var(--border)`, …). Tailwind is installed and imported but rarely used beyond resets.
- Dark mode = `darkMode: "class"` + `.dark` class on `<html>`; color tokens have light/dark values in `index.css`. The toggle sits in the `App.tsx` chrome, not in Profile.
- Do **not** hardcode hex colors; add or reuse a CSS variable.
- Animation: `framer-motion` (`motion.div`, `whileTap`). Icons: `lucide-react`.
- Layout is a phone-shaped column: screens are `flex: 1`, usually with `overflowY: "auto"`; fixed footers/nav live in `App.tsx`.
- Accessibility is minimal (icon-only buttons often lack `aria-label`); improve it in new code.

## 7. Conventions

- Components: default export, one screen per file in `components/`, props interface declared above the component.
- Services: pure functions for local array transforms (`postService`) and one `api` object for network calls.
- Naming: `handleX` for handlers, `onX` for props, `XScreen` for screens, `ApiX` for server DTOs.
- Keep `types.ts` as the shared contract; extend it before inventing per-component ad-hoc types.
- Dates in UI types are `number` (ms). API dates are ISO strings — convert at the mapper boundary.
- UI `Post.likes` is a `string[]` used mainly as a like-count holder (`length`), not a real user list. `Post.comments` is embedded in the UI type but fetched separately.
- `strict` + `noUnusedLocals` + `noUnusedParameters` are on; unused props/imports fail typecheck.

## 8. Gotchas / traps

1. **Hardcoded user id in Pages:** `PageManagementScreen` and `PageViewScreen` still receive `CURRENT_USER_ID` (`'u1'`), not `currentUser.id`. Chat was fixed to use the real id; page roles remain wrong for any other signed-in account.
2. **Reels are not video-only:** `ReelScreen` takes the six most recent posts regardless of `mediaType` and shows a play overlay.
3. **Reels/comments user lookup:** components resolve authors from the merged `users` array; an author missing from it renders blank. `mergeUsers` only adds API users that appeared in a fetched post/comment.
4. **`initialPages`/`initialProducts` ids are fake** (`u*`, `page*`, `p*`) and do not exist in the backend. The chat entry points resolve demo ids (`u2`…) to real accounts by searching the name; users outside the six seeded accounts show an alert instead. Resetting to real data means replacing `data.ts` seeds screen by screen.
5. **Marketplace seller identity is `CURRENT_USER_ID`** (`'u1'`), so "my listings" is always the demo user. "Message seller" only works for sellers whose names match a real account.
6. **Saved posts are per-session** and toggled by id with no API call; `PUT /posts/:id/save` is designed but not built.
7. **Chat relies on Neon latency:** API calls can take 1–5s, so the socket ack timeout is 15s. Never shorten it below the API's slowest query path.
8. **No error boundary**; unexpected render errors blank the app. API errors generally surface via `window.alert` or inline `authError`.
9. **`loadFeed` is N+1** (1 + one request per post). Watch this when adding infinite scroll.
10. **Theme default is dark** (`localStorage !== "light"`); the toggle is rendered in the `App.tsx` top chrome.
11. **Bundled single-port build** serves `apps/backend/public`; a stale copy can shadow the Vite dev server only in that mode, not in `npm run dev`.
12. **`SpeedInsights` is mounted in `App.tsx`** (Vercel). It is harmless locally but requires the Vercel deployment for data.
13. **A socket `chat:error` disconnects the client** (bad/expired token); the UI currently only surfaces it through failed requests, so re-login is the recovery.
14. `apps/ui/dist` is gitignored; don't hand-edit it.

## 9. What to touch when adding a feature

1. Extend `types.ts` (UI shape) and `services/api.ts` (request + mapper) if the server is involved.
2. Add the screen/flow state in `App.tsx`; keep server data in `App.tsx` or a dedicated context — do not duplicate it in `PageContext`.
3. Add the route branch in `App.tsx`; add a `BottomNav` item only for top-level destinations.
4. Style with CSS variables + inline styles; reuse `Dialog`, `Avatar`, `CommentDialog`.
5. Verify with `npm run typecheck --workspace @mononet/ui` and `npm run lint --workspace @mononet/ui`.
6. If you replace a local prototype with API data, remove the `data.ts` seed for that domain and update §5 of this file.

## 10. Backlog aligned with the API design

Ordered by what unblocks the most UI:

1. Saved posts (`PUT/DELETE /posts/:id/save`, `GET /users/me/saved`) — replaces `savedPosts`.
2. Comment editing (API has no endpoint yet) — removes the local-only branch.
3. Notifications from the server (`GET /notifications`, unread count) — replaces `initialNotifications`/`pushNotification`.
4. Pages API — replaces `PageContext`; first fix the hardcoded `CURRENT_USER_ID` props.
5. Marketplace API — products, cart, orders replace `initialProducts`/local cart/orders.
6. Chat polish: unread badge in the nav, message edit/delete, group conversations, Redis adapter for multi-instance.
7. Pagination/infinite scroll on the feed; split `loadFeed` into post page + lazy comment fetch.
8. Reels: filter by video, add real view/save endpoints.
